# 设计状态与变更治理

本页用于让 agent 在“忠实实现”“最小修复”和“真正探索”之间作出可审查的选择。它不要求每个项目新建设计系统文档。

## 先分类，再动手

| 状态 | 何时使用 | 可以做什么 | 不能做什么 |
| --- | --- | --- | --- |
| `LOCKED` | 有用户批准的 Figma、截图、代表流程、设计合同或明确方向 | 为响应式、可访问性、平台约束和已证实的缺陷做最小适配 | 借“优化”改视觉语言、信息层级、比例、密度或主要流程 |
| `EXISTING` | 没有批准稿，但仓库已有可复用组件、token 或相邻模式 | 查调用者并复用；在共享根因处修复；记录必要推断 | 无理由新建平行组件、覆盖 token 或只修 ticket 路径 |
| `EXPLORE` | 没有可复用模式或批准方向，且任务确实需要新设计 | 提出 2–3 个可比较方向，说明任务、取舍和验收；选定后将该范围锁定 | 把一个未经选择的方向扩展成大范围实现，或伪称为既有规则 |

用户明确批准某个探索方向后，该方向在本任务内转为 `LOCKED`。用户只要求修复缺陷时，不把它升级为视觉重设计。

## 最小记录

为每个重要表面保留下列一行；可放进项目 `DESIGN.md`、已有设计合同或交付回复。

```text
表面：任务编辑弹窗 / 状态：EXISTING / 依据：当前组件和 390px 截图 /
允许改动：共享布局与焦点行为 / 禁止改动：品牌色和保存语义 /
验收：长标题、200% 文字、键盘关闭、保存失败保留输入。
```

当任务跨多个页面或要新增/替换共享 token、组件或流程时，才建议创建或更新项目级 `DESIGN.md`、token 源和 `VISUAL_QA.md`。一屏审查或小修复使用上面的记录即可。

## 执行边界

- `LOCKED` 中发现无障碍或平台缺陷时，只改能解决缺陷的最小部分，并说明偏离原因和渲染证据。
- `EXISTING` 先查真实调用者；共享问题用一个真实主流程验证，再抽查相邻调用者。
- `EXPLORE` 的选择需要用户批准，除非用户已经给出明确方向和实施授权；即使如此也要保留被排除的替代方案及原因。
- 每次状态切换都记录“谁批准、何时、影响范围”。没有证据时写 `未确认`，不要把推断标为批准。
- 代码、浏览器、模拟器、原生壳和真机是不同证据。一个环境的通过不能替代另一个环境。
